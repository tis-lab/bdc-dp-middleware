## 2026-10-28 09:43 PDT: es image for OpenShift (Dockerfile-OpenShift)

- New `es/Dockerfile-OpenShift` for an OpenShift BuildConfig from GitHub
  (`contextDir: backend/es`). It matches `es/Dockerfile` except that it also
  copies `es/root-openshift/` and ends with numeric `USER 1000:0`.
  `es/Dockerfile` and compose are unchanged.
- `es/root-openshift/.../elasticsearch.yml` replaces the shared one and adds
  `node.store.allow_mmap: false` (nodes usually keep `vm.max_map_count` at
  65530). Shared settings are duplicated and must be kept in sync.
- `ES_JAVA_OPTS` is not in the image. ES sizes the heap from the pod's memory
  limit, or the Deployment can set `ES_JAVA_OPTS`.
- Verified: the image builds, and with `docker run --user 1000770000:0 --memory
  2g` the cluster is green, indexing works, the heap is 1 GB and `allow_mmap` is
  false. The compose stack is unchanged, so its checklist was not rerun.
- README and DEV.md updated.

## 2026-10-25 16:06 PDT: GraphQL data model project (model/)

- New standalone Maven project `model/` (`org.biodatacatalyst:bdc-dp-model`,
  Java 25, own Maven wrapper), moved here from the repo root. It holds
  generic starter schemas `common.graphqls` (enum), `query.graphqls` (inputs)
  and `response.graphqls` (output types), with no root types; the app's API
  schema will own `Query`.
- Java is generated by DGS codegen (`graphqlcodegen-maven-plugin` 3.10.1) into
  `src/generated/java`, which is committed. A normal build only compiles it
  (build-helper `add-source`). `./mvnw -Pgenerate generate-sources` wipes the
  directory, then regenerates it. `onlyGenerateChanged=false` is needed: with
  the default, the second run left the directory empty. Classes carry a
  dateless `@Generated`.
- New `bin/check-model-drift.sh`: regenerate, then fail on any change under
  `src/generated` per `git status` (exit 1 drift, 2 generation failed).
- Verified: `./mvnw clean verify` passes (2 tests) and leaves `src/generated`
  untouched; regenerating twice is byte-identical. In a throwaway git repo the
  script returned 0 when clean, 1 for an added field (`M`) and a removed type
  (`D`), and 2 for a schema syntax error. Codegen accepted a field of an unknown
  type (reported as drift); `ModelSchemaTest` is what catches that.
- README, DEV.md and CLAUDE.md updated. The compose stack is unchanged, so its
  checklist was not rerun.

## 2026-10-13 15:29 PDT: pg init SQL folder (pg/init-sql)

- New `pg/init-sql/` (with `.gitkeep`), bind-mounted read-only at `/init-sql`.
  When the cluster is created, the new image script
  `docker-entrypoint-initdb.d/20-init-sql.sh` runs its `*.sql` files in byte
  order (`LC_ALL=C`), after `10-dp.sql`, as `dp` in database `dp`, with
  `ON_ERROR_STOP`. Changing the SQL needs no rebuild, only `bin/clean-pg.sh`.
- `pg/.dockerignore` keeps `init-sql/` out of the build context.
- Tested in throwaway containers (uid 1234, tmpfs data): `01-`, `02-`, `10-`
  ran in order; the tables they created are owned by `dp`; `.gitkeep` and a
  `.txt` file were ignored. A failing `02-` stopped init before `03-`, and the
  container exited with code 3.
- Recreated the live `pg` container with the new image and mount. It's
  healthy; existing data was kept (init doesn't re-run on it).
- Updated README, DEV.md and CLAUDE.md (the exception to the `root/` rule).

## 2026-10-13 15:09 PDT: PostgreSQL service (pg)

- New `pg` service built from `pg/Dockerfile`: `FROM postgres:${PG_VERSION}`
  (`PG_VERSION=18.6` in `.env`), plus pgvector from the PGDG apt repo, plus
  `ENV POSTGRES_HOST_AUTH_METHOD=trust`. Port 5432. Runs as the invoking user
  with the usual `user`/`group_add` block.
- `./data/pg` (with `.gitkeep`) is mounted at `/var/lib/postgresql`, because
  PostgreSQL 18+ images keep `PGDATA` in `18/docker/` below it.
- `pg/root/docker-entrypoint-initdb.d/10-dp.sql` creates the login role `dp`
  (not a superuser) and the database `dp`, owned by `dp`, with the `vector`
  extension and `public` owned by `dp`.
- Healthcheck: `pg_isready -h 127.0.0.1 -U dp -d dp` (over TCP, so it doesn't
  pass while the init scripts are still running).
- New `bin/clean-pg.sh`: confirm, `rm --stop --force pg`, empty `data/pg`,
  `up -d --wait <args> pg`. Leaves es/kibana running. Tested under Bash 3.2
  with a stand-in `docker`.
- Verified: all three services healthy; `pg` runs as `uid=1000 gid=1000
  groups=1000,0`; `data/pg` is owned by 1000:1000; pgvector 0.8.7 works for
  `dp`. (`find data ...` also lists older `data/es` and `data/kibana` files with
  group `docker` (986), which were written when the primary gid was 986. That
  predates this change.)
- Updated README, DEV.md and CLAUDE.md.

## 2026-10-01 06:48 PDT: clean-es.sh

  empties `data/es` (keeping `.gitkeep`), then runs `./compose.sh up -d --wait`.

## 2026-10-01 06:42 PDT: macOS compatibility

- `compose.sh` now finds its directory with
  `cd -P "$(dirname "${BASH_SOURCE[0]}")" && pwd` instead of `readlink -f`.

  current directory as the project folder.
- Checked:
  - the script works under Bash 3.2 (the version macOS ships)
  - both Elastic images have arm64 builds
  - ES and Kibana run as a typical macOS uid:gid (501:20)
- README: macOS requirements (at least 4 GB memory for the Docker VM),

  exits (code 137).

  maps file ownership to the Mac user, so the ownership check only proves

## 2026-10-01 06:25 PDT: Initial Elasticsearch + Kibana stack

- Created the `backend/` compose project. Its `es` service builds from `es/`:
  `FROM docker.elastic.co/elasticsearch/elasticsearch:${ES_VERSION}` followed
  by `COPY root/ /`.
- `ES_VERSION=9.5.3` in `.env`. Elastic publishes no `latest` tag, so the
  version is pinned and shared with Kibana.
- `es/root/usr/share/elasticsearch/config/elasticsearch.yml`: single node,
  security and TLS disabled.
- Compose settings for `es`:
  - 2 GB heap
  - ports 9200 and 9300
  - memlock/nofile ulimits
  - a cluster-health healthcheck
  - data at `data/es`
- Added a `kibana` service (port 5601) that waits for `es` to be healthy.
- Fixed a startup failure. `COPY root/ /` reset `config/` to root:755, so ES
  couldn't write its keystore. The Dockerfile now restores the ownership and
  mode after the copy.
